# Orchestrator

Saved teams contain ordered agent IDs and, optionally, assigned folders. Starting a mission creates a durable mission record and invokes each selected agent against a real configured provider, passing the task and prior outputs as context. Each result is persisted as a mission event and streamed to the UI. A failure marks the mission failed; a successful sequence marks it completed.

## Assigned folders

When a team has folders assigned (Settings → Équipes), the main process builds a listing before the first agent runs and appends it to every participant's first message, with one capability flag per folder: `[lecture seule]` or `[écriture autorisée]`, followed by the available action markers. Agents can request a file with a full line `READ: <relative path>`. When at least one folder is writable, agents can also emit `WRITE: <relative path> | <content>` (single line, `\n`/`\t` escapes supported, 512 KB max), `MKDIR: <relative path>` and `DELETE: <relative path>` (file or empty folder — no recursive deletion). When the team allows launching applications, agents can emit `RUN: <program and arguments>` (launch without waiting, bounded output snapshot) and `RUN_WAIT: <program and arguments> | <working subfolder>` (waits for exit, 120 s max, reports the exit code). Every marker is parsed out of the streamed answer, resolved by the main process, and the tagged result (`FILE_CONTENT`, `WRITE_RESULT`, `MKDIR_RESULT`, `DELETE_RESULT`, `RUN_RESULT`) is sent back as the next message of the same conversation. A mission turn allows at most 3 rounds, 6 actions per round and 2 MB of writes per turn.

Resolution is confined by construction: requests must be relative, `..` and absolute paths are refused, and each candidate is resolved to its real path (symlinks included) then verified to sit inside one of the assigned folders — write targets are anchored on their deepest existing ancestor so a symlinked parent cannot smuggle a path out. RUN programs must be a bare name resolved on the PATH or a path inside the assigned folders; arguments that look like out-of-root paths are refused; there is no shell interpolation (only `.bat`/`.cmd` run through cmd.exe). Refusals are reported to the agent as tagged text instead of leaking content. See `electron/workspace.ts`, `shared/workspace-flags.ts` and their tests, plus the end-to-end mission tests with a scripted SSE provider.

## Scope

The current scheduler is sequential and bounded by team size. It does not autonomously plan subtask dependencies or execute file changes (file access is read-only, within assigned folders only). Cancellation and mission stop are exposed, though the current renderer's stop control needs the active mission ID wired before relying on it; use this workflow with that limitation in mind.
