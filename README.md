# OpenHarness

**One Platform. Multiple AI Agents.** Open-source AI Agent Desktop Platform.

OpenHarness is an Electron desktop application for individual AI-agent conversations and persisted, sequential team missions. Provider calls run in the Electron main process; conversations and mission events are stored locally in SQLite.

## Requirements

- Node.js 20 or later and npm.
- Windows, Linux, or macOS for development. Native installers should be built on their target OS.
- A provider API key (OpenAI API billing is separate from ChatGPT subscriptions). Custom OpenAI-compatible endpoints such as Ollama can omit a key.

## Development

```sh
npm install
npm run dev
```

Configure providers in Paramètres. The Claude and OpenAI connectors use their official endpoints (`api.anthropic.com`, `api.openai.com`) — you only enter the API key and model. Custom connections are OpenAI-compatible Chat Completions with a user-supplied Base URL, for example `http://localhost:11434/v1` or `https://api.deepseek.com/v1`.

## Build and tests

```sh
npm test
npm run typecheck
npm run build
npm run build:win
npm run build:linux
```

Windows and Linux packaging should be run on their respective OS. Release artifacts are placed in `release/`. A successful source build does not establish that both OS installers have been produced; confirm artifacts on each target runner.

The Windows setup (`OpenHarness-Setup.exe`) is an assisted NSIS installer: it asks for the interface language (French/English, defaulting to the OS language), shows the license, lets the user pick per-user or per-machine installation with the installation directory, and can launch the app at the end. The application itself is bilingual with a language switch in Settings; the choice is stored locally and the OS language is used as the initial default.

## Current scope

Included: isolated Electron renderer, validated IPC allowlist, local SQLite, OS-protected API keys, Anthropic and OpenAI-compatible streaming, ten built-in agents, custom agent creation, conversation history, saved teams, sequential real-provider team missions, mission events, cancellation plumbing, and per-team assigned folders with per-folder read/write capabilities during missions (`READ:`/`WRITE:`/`MKDIR:`/`DELETE:` request cycle with symlink-safe path confinement) plus optional application launching (`RUN:`/`RUN_WAIT:`) gated by a team-level switch.

Not yet implemented: file attachment/content tools, undo/rollback of agent file writes, concurrent/dependency-aware scheduling, provider model discovery, custom-agent edit/duplicate/disable flows, mission resume/history UI, web-search tools, human approval gates, macOS notarization, and comprehensive end-to-end provider tests. The team workflow is sequential delegation, not a fully autonomous task-planning graph. No provider calls are mocked in the application.

## UI

Dark and light themes with a shared token system (`src/ui/style.css`). Papicons render through a single mapping component (`src/ui/icons.tsx`); the Electron application menu is removed for a clean desktop frame. App icons are generated by `build/make-icons.py` into `build/icon/` and referenced by electron-builder for Windows and Linux.

## Security notes

Renderer has `contextIsolation`, `sandbox`, and `nodeIntegration: false`; preload exposes an allowlisted IPC interface. API secrets use Electron `safeStorage` and are not returned to the renderer. Never load untrusted remote content into the privileged app. Network access is needed for remote providers. Review and configure operating-system protections before using production credentials.
